実装したい機能を広げすぎるとポートフォリオとして完成させにくくなるため、「今回実装」「将来拡張」「対象外」を明確に分けました。
棚卸、佐川急便API連携、ハンディターミナルによるピッキングなどは将来拡張とし、今回の開発範囲を現実的な規模に整理しました。

業務スコープと機能スコープが混同しやすかったため、「業務としてどこまで扱うか」と「システムとして何を実装するか」を別々に整理しました。
これにより、手作業として残す工程とシステム化する工程を明確にしました。

ピッキング業務をどこまで対象にするか迷ったため、システムではピッキングリストの作成・印刷までを対象とし、実際の商品取り出しは手作業として対象外にしました。
将来的なハンディターミナル導入との境界も明確にしています。

出庫・配送・出荷の境界が曖昧だったため、出荷情報の確定まではシステム対象、実際の商品搬出や佐川急便による配送はシステム外として整理しました。
これにより、物流業務全体を無理にシステム化しない構成にしました。

在庫管理の範囲を検討する中で、オリコン単位の在庫移動まで実装すると機能が複雑になるため、今回は対象外としました。
一方で、将来的にはオリコンを丸ごと移動する方式で拡張できるよう、運用ルールを残しています。

利用者ごとの業務とシステム権限を混同しないよう整理しました。
仕入れ担当、入荷担当、在庫管理担当、出荷担当などの業務ロールは定義しましたが、担当者別の詳細なアクセス制御は今回実装せず、将来拡張としました。

出荷時の在庫不足を当初のスコープで十分に考慮できていなかったため、部分引当・一部出荷・未出荷数量の保持・在庫補充後の再引当を追加しました。
注文を作り直さず、同じ注文から複数回出荷できる構成へ改善しました。

外部システムとの連携範囲が広がりやすかったため、仕入先・卸先とのCSV受け渡しはメール＋手動取込を今回の範囲とし、ファイル共有や自動取込は将来機能として切り分けました。
これにより、今回実装と将来構想を明確に分離しました。

認証・バックアップ・権限管理などの非業務機能もすべて実装すると規模が大きくなるため、今回は社員マスタを利用した最低限のログイン認証に限定しました。
実運用向けの高度なセキュリティやバックアップは将来対応として整理しています。

スコープ整理後も業務フローやユースケースとの間に不足がないか見直し、在庫引当や未出荷分の再引当など、後から判明した機能を各スコープへ反映しました。
資料を一度作って終わりにせず、後工程で見つかった不足を前工程へ戻して修正する形で整合性を高めました。
